# Cloudflare static frontend

Preparation starts from deployed commit `1014a2616a25cd88d85f10b499f0f3e86d469d28`, Amplify job 28. The existing Vite frontend build is `npm run build` (TypeScript plus Vite); upload only `dist/` to Pages project `vinoveil`, production branch `main`.

The tracked `amplify_outputs.json` is empty. Amplify production replaces it with generated public Cognito/AppSync configuration before the build. A Cloudflare build from the tracked empty file would lose working backend connections. Put the complete real generated outputs from the current production backend into Production environment secret `AMPLIFY_OUTPUTS_JSON`, because it includes a browser AppSync API key. The workflow requires user-pool/client IDs, data URL and model introspection before overwriting the empty file for the build. Do not place server credentials into this public JSON or commit generated outputs. The upload records a dirty checkout because it deliberately injects this generated public file; the revision still identifies the application source.

The current Amplify app/branch has no configured `VITE_*` settings. The workflow preserves all existing source defaults and does not introduce Shopify, site-URL or waitlist overrides. Branch `CONTACT_FROM_EMAIL` and `CONTACT_SES_IDENTITY_ARN` settings belong to the retained backend and are not frontend variables.

The manual-only, main-only workflow installs existing locked dependencies, runs unit tests before injecting production configuration, restores generated outputs, builds and uploads through pinned deployment-only Wrangler 4.129.0. Configure secret `CLOUDFLARE_API_TOKEN` and variable `CLOUDFLARE_ACCOUNT_ID`. It never invokes `ampx pipeline-deploy` or mutates the existing Cognito/AppSync/Lambda/SES/order backend. A three-field lock correction updates only the existing dev-only `semver` entry from 7.8.2 to 7.8.5 so `npm ci` can validate the lock; direct dependencies and other locked entries are unchanged.

The old `public/_redirects` rule `/* /index.html 200` has been removed because Pages applies it even to existing assets, which would return HTML for JavaScript/CSS. Keep no root `404.html`; native Pages SPA fallthrough supports application routes and leaves existing assets accessible. The unrecognized `public/redirects` file remains unchanged as existing source data. The operator must verify missing-asset behavior against the real previous host and handle any required difference before production cutover; this preparation does not invent a new fallback server.

Use the recovered production bundle without its `_redirects` metadata for the first upload. Its generated public configuration is already compiled into the bundle. The workflow requires the real generated outputs/settings before a future rebuild; a successful build with the empty tracked configuration would not establish production parity. Authentication/contact/active checkout, source imagery, deep links and custom domains remain deployed acceptance gates.
